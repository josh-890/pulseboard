## 1. Data Flow

```
Read path:
  PostgreSQL → Prisma Client → async services → Server Components → Client Components
               (lib/db.ts)     (lib/services/)   (app/ pages)       (components/)

Write path:
  User interaction → Server Action → Zod validation → Service → Prisma → PostgreSQL
  (Client Component)  (lib/actions/)                   (lib/services/)    + revalidatePath()

Media path:
  File upload → /api/media/upload → Sharp variants → MinIO storage → MediaItem record
                                     (media-upload.ts)                  (media-service.ts)
```

## 3. Service Layer

All services in `src/lib/services/`. All functions are async, return Promises. Services are the only layer that touches Prisma.

### Core Services

**`person-service.ts`** (~1,350 lines) — Person CRUD, paginated listing, work history, connections, affiliations, current state derivation, entity media queries, cover photos

**`media-mark-service.ts`** (2026-10-16) — The photo marks iconic / ★ / outtake. ★ is `MediaItem.isFavorite`; iconic and outtake are tags. `getMarkTags()` → `{iconic, outtake}` as `PaletteTag`s: the tag of that slug in the `judgment` group (else another group's), created in Judgment when missing (pulse had no `outtake`). Exposed by `getMarkTagsAction` and the client store `hooks/use-mark-tags.ts` (one load per page). `components/gallery/media-marks.ts` holds the one definition of the three marks (icon, colours, label, viewer keys `,` outtake · `.` ★ · `-` iconic — rising left to right like the ladder) and `itemMarks(item, markTags)`; the lightbox toolbar (toggles through its `useEntityTags` controller, keys in its keydown handler), `GalleryTileMarks` on every `GalleryThumbnail`, the `MEDIA_ITEM` bulk bar (`BulkTagControls`, tri-state from `stateOf`) and the person showcase chip all use it. **Tiers (2026-10-17):** outtake < ★ < iconic; `lib/media-mark-tiers.ts` `markCascade(key, on)` gives every mark a change sets (the lower ones) or clears (the higher ones). The server enforces it in `cascadeMarks(tx, mediaItemIds, changes)`, called by every MEDIA_ITEM write in `entity-tag-service` (add, remove, replace via a before/after diff, bulk add/remove; `markChangesForTags` picks the iconic/outtake slugs out of the tag ids) and by `setMediaFavorite(ids, on)` (used by `setMediaFavoriteAction` and `convertCollectionToFavorites`). The screens apply the same rule at once: the lightbox's `setMark` (keys, toolbar, info-panel ★, palette/slot on a mark tag), `GalleryTileMarks` overrides, and `BulkTagControls` reporting the implied tag + `isFavorite` through `BulkTagChange` to `applyTagChangeToItems`. **Protected (2026-10-17):** `lib/protected-tags.ts` (`PROTECTED_TAG_SLUGS`, `isProtectedTag`) — `tag-service` `assertNotProtected` refuses deleting (`deleteTagDefinition`; `deleteTags` checks the whole selection first), merging away (`mergeTagDefinitions` sources) and renaming (`updateTagDefinition`, the slug follows the name); the catalogue tree, `TagRowMenu` and `TagEditPanel` hide those actions.

**`person-showcase-service.ts`** (2026-10-16) — The person Overview's showcase. `getPersonShowcase(personId, {size=48, day?})` → `{items: ShowcaseItem[] (GalleryItem + source iconic/favorite/outtake/random), curatedCount}`: one SQL pass over the photos that show the person (the `imageShows` rule of tag-predicates — on-camera SessionContribution not hidden via `media_item_hidden_person`, or `PersonMediaLink` — written set-based as a UNION of the two indexed ways in; an OR scanned every image), excluding `decodeIssue` and `isAnnotation`; level iconic (tag slug) > `isFavorite` > outtake (tag slug) > random, the random level only from non-REFERENCE sessions; ordered by level, iconic by tag `createdAt DESC`, the rest by `md5(id || personId:day)` (daily rotation in the display zone) — the random level round-robin over sets: a photo's set (min `setId` among the person's SetParticipant sets — SetMediaItem is indexed by set, not photo; session when in none) gives two photos per round (`row_number() OVER (PARTITION BY level, set) / 2`), sets in a daily order; then `getMediaGalleryItemsByIds`. Option `mode: "random"` + `seed` (the showcase's Random switch / Shuffle, via `getPersonShowcaseAction(personId, mode, seed?)` in person-actions, which also loads Best on demand): reference sessions excluded for every photo, one round-robin over all sets ignoring the level for the order (`PARTITION BY grp`), ordered by the caller's seed; the level still sets `source` for the chips; the result also carries `setCount` and its `mode`. `getPersonOverviewShowcase(personId)` (2026-10-17) is what the page loads: a random deal with a fresh seed per visit, falling back to Best when that is empty (reference photos only). `getPersonKnownFor(personId, limit=8)`: the person's Sets (SetParticipant) by `rating DESC NULLS LAST, releaseDate DESC NULLS LAST` with `getCoverPhotosForSets` covers.

**`media-origin-service.ts`** (2026-10-18) — `getMediaItemOrigin(mediaItemId)`: the image's sets (`SetMediaItem`, earliest `releaseDate` first), its session and, for a reference session, its person; the **people shown** = `getOnCameraCastForSessions` minus `getHiddenPersonsForMedia` (ADR-0023), named `Name (ICG-ID)`. A copy without sets of its own answers for its `copiedFromMediaItem` (`imageId` = that source). `lib/media-origin-href.ts` turns it into the "back" target: first set → `/sets/<id>?photo=<imageId>`, else reference person, else session.

**`media-service.ts`** (~1,130 lines) — MediaItem CRUD, gallery item construction (`toGalleryItem`), person/session/set gallery queries, headshot management, usage/link management, batch operations, duplicate detection, similar image search. `getPersonEntityMedia`/`getPersonMediaForEntity` return a body feature's photos ordered by `[sortOrder, createdAt]` (first = body-map hover cover). `setEntityMediaCover(personId, entityModel, entityId, mediaItemId)` makes a photo the cover by rewriting `PersonMediaLink.sortOrder` **scoped by the entity FK** (`moveToFront` helper) so the same image's other links are untouched — distinct from `reorderPersonMediaAction` which is `{personId, mediaItemId}`-scoped. `getHeadshotsForPersons(personIds, slot?)` resolves the displayed framing per person (ADR-0016): no `slot` → the avatar = the **representative** of the avatar-source (Headshot) Profile category; `slot=N` → the representative of `cat_profile_slot{N}` (the people-browser framing selector). `HeadshotData` carries `mediaItemId` so the hero lead de-dupes against the gallery. (The legacy `slot`/`isAvatar` columns + `HEADSHOT` links + `getPersonHeadshots`/`getPersonSlotState`/`getFilledHeadshotSlots` were retired in ADR-0016 slice 6e-2.)

**`set-service.ts`** (~820 lines) — Set CRUD, `buildSetWhere(filters)` (the list's where — shared with the rating queue), credit resolution, participant rebuilding, session link management, media bridging (`addExistingMediaToSet`, `syncSetSessionLinks`). `getSuggestedResolutions(rawName, channelId)` uses a three-tier priority: (1) alias+channel exact match ("Known alias on this channel"), (2) previously-resolved same rawName, (3) frequent in channel. `resolveCreditRaw()` auto-matches `rawName` to `PersonAlias.nameNorm`, sets `resolvedAliasId`, populates `creditNameOverride` on `SessionContribution`, and returns `suggestNewAlias: true` when no alias exists.

**`session-service.ts`** (~450 lines) — Session CRUD, `buildSessionWhere(filters)` (the list's where — shared with the rating queue), merging, reference session management (auto-created per-person, type=REFERENCE). Merge (2026-10-21): a contribution the surviving session lacks is **re-pointed** (`sessionId` updated — intensity, Era and resolved alias come along; it used to be deleted and re-created, losing the Era); for the same person + role in both, `mergeContributionIntensityInTx` carries intensity over

**`intensity-service.ts`** (ADR-0036, slice 2) — `getSessionIntensity(sessionId)` (the leads — `LEAD_ROLE`, ADR-0037; someone only appearing carries no intensity: person `Name (ICG-ID)`, role, extra ids, acts with their ADD/DROP departures, `suggestScenarioIds` from the others' `sexAtBirth`); `setContributionExtras` / `setContributionsExtras(entries)` (≤1 per group), `setContributionAct` / `setContributionsAct(ids, actId, ticked)`, `setContributionActExtras(actRowId, wantedIds)` (stored via `overridesFor`), `setContributionActNote`, `restoreContributionActs(items)` (undo), `copyContributionIntensity(from, to)` ("Same as…"; the target is to review again), presets (2026-10-24): `applyIntensityPreset(contributionIds, presetId)` (leads only, refuses support; adds the acts each lacks with `presetId`, lays the preset's extras over theirs via `presetAdditions` — a grouped one replaces —, clears `intensityReviewedAt`; returns a `PresetUndo`), `undoIntensityPreset(undo)` (drops the acts still from that preset, restores extras and review state), `setIntensityReviewed(contributionIds, reviewed)` (leads only); like last time (2026-10-27): `getIntensityHints(sessionId)` → `{ channel, usual, lastTime }` (the session's channel — primary set's, else first released, as the queue —; per lead contribution its source via `pickLastTime` over the person's other confirmed lead contributions with acts, with acts/extras; `usual` via `usualPreset` over preset ticks of confirmed leads in other sessions of the channel), `copyIntensityLikeLastTime(pairs)` (same person, other session, confirmed source; adds missing acts with departures, extras via `presetAdditions`, to review; returns a `PresetUndo` with `presetId` null — `undoIntensityPreset` takes it back); `getSetIntensity` gives each session its `hints`; `getSessionIntensity` returns `reviewed` and each act's `presetId`; `getContributionsSessionId(ids)` (refuses a mix), `mergeContributionIntensityInTx(tx, from, to)` (a duplicate act's photos join the act that stays), evidence (3b): `setActsEvidence(actRowIds, mediaIds, linked)` (gallery selection, viewer), `setActEvidence(actRowId, mediaIds)` (the panel's picker, replaces), both linking only photos of the act's session, `getContributionActsSessionId(ids)`, `getPersonActEvidence(personId)` (act id → thumbs, oldest session first); `getSessionIntensity` returns each act's `mediaIds`; `getSetIntensity(setId)` (2026-10-24: a set's sessions with their intensity, `shared` when a session has other sets, the acts the set leaves out — `SetActExclusion` — and the acts with an evidence photo in the set), `setSetActExcluded(setId, contributionActId, excluded)`; `getPersonIntensity(personId)` (slice 3 — on-camera contributions with acts or extras → `summarizePersonIntensity` in `src/lib/intensity-person.ts`: sessions oldest first, undated last, value per session, peak, scenario peaks, mean, per act count/best/first dated session). **`session-merge-candidates.ts`** (2026-10-18) — the session merge dialog's data. `getSessionMergeCandidates(sessionId, query?)` → `{ self, candidates }` (PRODUCTION only): without a query the pool is sessions sharing an on-camera person (`SessionContribution`, not `BEHIND_CAMERA_GROUP`), a label (the session's `labelId` or a linked set's `Channel.labelId`) or the project (capped at 600), scored 3·shared people + 2·label + 1·project + 2 (≤30 days) / 1 (≤90 days) between earliest set releases, score > 0, top 20; with a query the pool is name / set title / channel / person alias or ICG-ID / label matches (top 50), ranked the same way. ### Import Pipeline Services

All import services in `src/lib/services/import/`.

**`parser.ts`** — Pure function: raw file text → `ParsedImportData` (person profile, digital identities, channel appearances, sets with co-model references, co-model directory). Handles edge cases (PowerShell artifacts, em-dash nulls, duplicate detection). One forward pass with one cursor, so the header must hand that cursor to the next section: it ends at the `=== Links aus 'Other Links' ===` marker **or** at the first `Channel :` / `Titeltxt :` line, because Other Links is optional and a file without it used to run the header loop to EOF (Hilary C, AX-00ET: 454 sets parsed as 0). **Header keys are single-valued — the first occurrence of each wins** (`takeHeaderKey`), because that terminator is still the only one the header has: when a scrape fails to strip tags at the `Biography :` field the rest of the page lands *ahead* of it, and every thenude.com gallery credit is an anchor whose `title` attribute carries a newline, so lines reading `ICGID: MB-003G" class="model-title">…` match `startsWith('ICGID')`. Under plain assignment the **last** of 93 such lines won: Matilda Bae (MB-003G) staged 111 sets under an ICG-ID with HTML welded to it, every `subjectPersonId` resolved to null, and the cover basket — whose candidate list is `subjectPersonId OR subjectIcgId` — matched nothing. Hand-correcting the real header line could not help, it was overwritten 92 times below. 4 of 164 xpulse files carry the shape; guarding assignment leaves the cursor exactly where it lands today (verified: 163 of 164 files re-parse byte-identical). Repair for rows written before this: `scripts/repair-malformed-subject-icgid.ts`. **`checkParseCoverage(content, parsed)`** counts the block shapes the parser itself keys on straight off the raw text and reports any section the file demonstrably holds that came out empty — a total-failure check only, deliberately silent on partial shortfalls. It **reports, never refuses**: `createBatch` still imports everything that parsed and writes `describeShortfalls()` to `ImportBatch.notes`, surfaced amber in the upload modal (which then drops the "Import complete" heading) and permanently in the `ImportWorkspace` header. `createBatch` returns `CreatedBatch` = batch + `parseShortfalls`. `ParseShortfall` is a discriminated union: `kind: 'section'` is the coverage check above; **`kind: 'malformedIcgId'`** fires when the parsed ICG-ID fails `ICG_ID_RE` — the identity key is the one field whose corruption is silent (the import succeeds, the sets stage, nothing resolves to a person), so it is reported on the same amber surface. Reported, never repaired: the parser cannot know which part of a polluted string was meant.

**`matcher.ts`** — Tiered DB matching: exact ID → fuzzy name (pg_trgm), **except for persons**. Functions: `matchPerson`, `matchChannel`, `matchLabel`, `matchSet`, `matchAllEntities`. Returns confidence scores (0.0–1.0). `matchPerson` is **exact-ICG-ID only** — the fuzzy tier was removed 2026-05-26 after it silently merged different people with similar names. On a miss it runs `findSelfAssignedNamesake` (ADR-0026) and reports a same-named self-assigned-ID person through `matchDetails` while leaving `matchedEntityId` null: an advisory pointer, never a match. `ImportItemDetail` renders `matchDetails` amber when nothing matched, green when it did.

Filters `hasPersonEvidence` (`stagingSetIdsWithPersonEvidence`, 72 rows on xpulse — the suggestion's folder carries a claim or marker for somebody the set credits) and `archiveNamesOthers` are resolved to id lists rather than Prisma filters: both compare two tables against a cast that has two shapes. `getStagingSetsFiltered` (paginated, filterable by status/person/channel/date/priority/search), `getStagingSetStats`, `getStagingSetComparison` (side-by-side diff vs production Set), `updateStagingSetFields`, `bulkUpdateStatus`, `markStagingSetPromoted` (copies `archiveKey` to promoted Set and linked ArchiveFolder), `getDuplicateCandidates(id)` (the staging set(s) that triggered a duplicate warning — confirmed: same `duplicateGroupId`; probable: same channel + release date AND `isDuplicate`, which excludes the split photo/video **sibling**, `StagingSet.siblingId`). **`import/cover-transfer.ts`** — `transferStagingCoverToSet(coverImageUrl, setId)`, run at promotion when the Set has no cover of its own. Downloads the staged cover from MinIO, re-generates the standard variants, and creates a MediaItem in the Set's primary session — under `session/{sessionId}/…` and carrying `hash` + `phash`, so it is an ordinary picture of the set rather than a species of its own invisible to `/media/similar`. **`isProvisionalCoverKey(key)`** (pure, unit-tested) decides whether the cover is a stand-in: `archive/…` is a 512 px thumbnail of one of the folder's own images and steps aside for the real upload (`Set.coverIsProvisional`, honoured by the cover assignment in `createMediaItemDirect`); `staging/…` is the publisher's cover art — a different photograph from anything in the set — and keeps the slot. **`archive-service.ts`** — Core archive filesystem ↔ DB sync layer.
- `parseRoots(value)` — parse settings value as `string[]` (supports JSON array and legacy single-string)
- `buildFolderName(dateStr, shortName, participant, title)` — pure function, builds folder segment `yyyy-mm-dd-{short} {person} - {title}`
- `buildExpectedPathForStagingSet/Set` — async, computes expected relative path for display
- `buildFullPaths(relativePath, isVideo)` — returns one absolute path per configured root (multi-root support)
- `runMatchingPass(tenant)` (folder→entity) / `runMatchingPassForItem(id, type, tenant)` (entity→folder) — **person-aware** matching over the channel+year window. The channel is taken by **owning Label** (ADR-0020, `sameLabelChannelCodes`): a folder coded `NBL` reaches a `NubileFilms` (`NBLF`) set because both channels belong to Label *Nubiles* and the disk files both under `NBL-Nubiles`. A sibling channel must share the **exact day** and, since 2026-10-25, the **person or the title** as well — `scoreArchiveMatch({ isSibling })` never gives a sibling MEDIUM (a Label publishes several sets a day: `MA Nancy A - Artica` went to GoddessNudes' "Set 8" on the day alone); the year-wide title window stays own-channel only (on xpulse it would add 1,076 mostly generic-title pairs against 161 exact-day ones). Guarded by `archive-match-label-scope.test.ts`. Scores each candidate by participant-name match (`parseFolderParticipant` extracts the person from the canonical folder name `YYYY-MM-DD-CODE Person - Title`; `folderPersonMatches` compares it against **all** of the entity's participant alias-norms + staging import names) and title `pg_trgm` similarity, then gates via `scoreArchiveMatch` (name match → **HIGH**; else title ≥ `HIGH_TITLE_THRESHOLD` 0.6 → HIGH, ≥ `MEDIUM_TITLE_THRESHOLD` 0.4 → **MEDIUM**, else **no suggestion**) and `pickBestArchiveCandidate` (HIGH → exact-day → similarity). Writes a SUGGESTED `ArchiveLink`; a folder for which nothing qualifies any more loses the suggestion an earlier pass (or a looser rule) stored — counted as `cleared` (2026-10-25). The person signal disambiguates same date+channel collisions; pure helpers are unit-tested in `archive-match-score.test.ts`.
- `upsertArchiveFolders(items)` — ingest scan results; detects renames (by path), moves (by `sidecarKey` → `ArchiveFolder.archiveKey` lookup), and new folders; propagates path changes to linked Set/StagingSet
- `confirmArchiveFolderLink(folderId, setId, type)` — propagates folder's existing `archiveKey` to Set/StagingSet, clears suggestion; returns `{ archiveKey }`. No UUID generation here — key is always already present on ArchiveFolder.
- `lib/archive-cast-gap.ts` — **`archivePeopleMissingFromCast(archivePeople, cast)`** (pure, unit-tested): who the archive names that the set does not credit. Counts your confirmed claims **and** hand markers (`FOLDER_ATTRIBUTION`), never catalogue suggestions — 5,074 machine guesses would flag half the browser. Outside the service layer because the staged-sets browser is a client component. Fed by `attachArchiveCastGap` (per page of staged-set rows), `stagingSetIdsWhereArchiveNamesOthers` (the `archiveNamesOthers` filter) and `getSetArchiveCastGap` (the Set page, which also reports whether the person is a curated Person — a promoted cast is `SetParticipant`, a cache of `SessionContribution`, and both require one, so a Contact-only name cannot be added at all).
- `attachFolderPeople(items)` — fills `ArchiveFolderEntry.people` for a page of rows: `claims` (`ArchiveFolderAttribution`) and `cast` (the credit list behind a CONFIRMED link, via `loadCasts`), kept apart per ADR-0028. A post-step over the finished list because the entry is assembled at three call sites and the cast cannot be reached by a join. Two queries per page (≤200 rows).
- `createStagingSetFromOrphan(folderId, overrides?)` — **the only place a folder becomes a staged set.** Staged set and link are written in one transaction; the link is an **upsert**: a SUGGESTED link (the matcher's guess, possibly to another staged set — the folder still lists under "No Set"; ~3,000 on xpulse) is replaced by the CONFIRMED one, a CONFIRMED link refuses with "This folder is already linked to a set" (2026-10-16: a plain create hit the `archiveFolderId` unique index and left the staged set behind). Writes `releaseDatePrecision: DAY` alongside the date (both sources are day-precise: the folder name carries a full `YYYY-MM-DD`, the dialogue's field is a day). It used to leave the schema default `UNKNOWN`, which propagates to the Set and the Session at promotion and makes `computeProductionAge` return nothing — a folder-born set showed **no participant ages at all** though the date and the birthdate were both stored. Repair for older rows: `scripts/repair-folder-date-precision.ts`. Both entry points route through `createStagingSetFromFolder` (attribution-confirm-service): the develop queue with the folder's attributions and no overrides, the archive row's dialogue with the operator's corrections. It reuses an existing staged set via `findExistingStagingSet` instead of creating a twin, carries the folder's cover, writes `titleNorm`, the CONFIRMED link with `archiveFieldsFromFolder`, `review.develop = DEVELOPED`, and leaves the set `PENDING`. Before this the dialogue built its own StagingSet through `createManualStagingSetAction` and differed on all five (participant unresolved, no cover, no duplicate guard, no review state, `APPROVED`) — that action is now the path for a set with **no** folder.
- `SuggestedFolderInfo.personEvidence` — `{ kind: 'claim' | 'marker'; names }` when the proposed folder carries **your** statement (a confirmed `ArchiveFolderAttribution`, else a `FOLDER_ATTRIBUTION` marker) about somebody the target set credits, matched by **ICG-ID**. Rendered as its own badge beside exact/approx in the staged-set row: the confidence measures structure (day, title), this says the identity is established. Deliberately **not** in `scoreArchiveMatch` — measured on 2,841 live suggestions, 68 carry a claim and 30 a marker and *none* would change tier, so a scoring rule would move nothing today while being free to misfire later. It does act as a **tiebreaker** in `pickBestArchiveCandidate` (`personConfirmed`), ranked above title similarity and below the exact day, and it never turns an unqualified candidate into a suggestion — same person + same channel + same year is true of dozens of pairs.
- `beatsIncumbent(challenger, incumbent)` + `rankArchiveCandidates(...)` (pure, unit-tested) — the matcher streams folder by folder and used to skip any staged set already carrying a link, so the **first** folder to arrive kept it however badly it fitted. Measured on xpulse: 550 of 2,837 suggested links hold a set whose day they do not share, and for **271** a folder that does share the day sat unlinked. A `SUGGESTED` incumbent is now contested, and only a **categorical** improvement wins: the challenger shares the release day and the incumbent does not, or the day is equally (un)matched and the challenger carries a confirmed person, or day and person are equal and the challenger is **HIGH** where the incumbent (its stored link confidence) is **MEDIUM** — on the same day, "the person or the title agrees" against "only the day does" (2026-10-25: `2017-10-05-MA Ginger Frost - Chilea` held the staged set *Artica* against `Nancy A - Artica`, which went elsewhere; guarded by `archive-match-incumbent.test.ts`). Promoted Sets are contested the same way (they used to be skipped once any folder suggested them). Title similarity never displaces — that is the signal behind "Feel Good"/"Feels Good" five months apart. Equal evidence keeps the incumbent, which makes the pass order-independent. A `CONFIRMED` link is never contested. When the best candidate is unwinnable the next is tried (`firstClaimable`), so a folder does not end empty while a free set sits one line below.
- `archiveFieldsFromFolder(folder)` (pure, unit-tested) — the archive fields a new link inherits: path, file count, video flag, and `OK` (or `MISSING` if the last scan could not find the folder). **Never `PENDING`** — that status means "a path was recorded, nothing has looked at it", which cannot be true of an `ArchiveFolder` row, since a scan created it. Shared by `confirmArchiveFolderLink`, `createStagingSetFromOrphan` and `linkFolderToStagingSet`; the latter two used to write `PENDING`, so a set developed from its own folder displayed a blue badge that reads as an unconfirmed link with no confirm button beside it. Repair for older rows: `scripts/repair-pending-archive-links.ts`.
- `rejectArchiveSuggestion(folderId)` — clears `suggestedStagingId/SetId` + `suggestedConfidence`
- `getSuggestedFoldersForStagingSets(ids)` → `Map<stagingSetId, SuggestedFolderInfo>` — batch query keyed by `suggestedStagingId`
- `getSuggestedFoldersForSets(ids)` → `Map<setId, SuggestedFolderInfo>` — batch query keyed by `suggestedSetId`
- `SuggestedFolderInfo` type: `{ folderId, folderName, fileCount, parsedDate, fullPath, confidence: 'HIGH'|'MEDIUM' }`
- `FullIngestItem.sidecarKey?: string` — optional field for scan script to report `_pulseboard.json` archiveKey, enabling cross-drive folder-move detection

**`archive-key-service.ts`** — `getArchiveKeyFolders(stagingSetId, tenant)` → `ArchiveKeyView { key, hasConfirmed, folders }`: the folders sharing a staged set's archive key — release day + channel code, widened by `sameLabelChannelCodes` — plus the near misses from `archiveKeyDays` (`src/lib/archive-key.ts`, pure: ±2 days, day/month swapped). One query on the `(parsedDate, parsedShortName)` index (photo/video as the set, not `missingOnDisk`, ≤100), with each folder's `ArchiveLink` and its target's title; `personMatches` (`folderPersonMatches` against the import names + the credited ICG-IDs' aliases) and `titleMatches` (trigram ≥ `HIGH_TITLE_THRESHOLD`). Sorted same day → most agreement → closest day. `sets`: every staged set (not PROMOTED) and Set with the same day and channel codes, of the same kind, with its people (`Name (ICG-ID)` — import participants, or SetParticipant + common alias) and the folder of its link (confirmed first) — this set first, then those without a folder. A promoted staged set is read through its Set. Feeds `ArchiveKeyPopover` via `getArchiveKeyFoldersAction`; linking reuses `confirmArchiveFolderLinkAction`.

**`archive-cover-service.ts`** — Cover thumbnails for archive folders (plan slice 1). `getCoverWorklist(scope?)` (LIKE-escaped, case-insensitive, path-separator-normalised), `setArchiveFolderCover`, `setArchiveFolderCoverError`, `clearArchiveFolderCover` (delete a cover in the browser so a single folder can be re-read — a cover swap is meant to be the exception, not a `-Refresh` sweep), `listCoverFailures`, `getCoverStats`. Agent: `scripts/archive-cover.ps1`.

**`attribution-worklist-service.ts`** — Read-only archive side of the catalogue join (ADR-0027). Serves **orphans** (what the join must explain) *and* **groundTruth** (folders already linked to a set with known participants), because a hit rate with nothing to check it against is not a measurement. Also ships channel→owning-label and **channel-scoped** aliases (ADR-0024) so the agent's tiebreakers compare like with like.

**`attribution-suggestion-service.ts`** — Stores what the join proposes and folds it into the unit an operator decides on (ADR-0027, plan slice 4). `parseSuggestionBatch` (pure; all-or-nothing validation), `ingestSuggestions` (replaces per `(folder, source)` in a transaction per folder — idempotent re-runs, other sources untouched), `getSuggestionStats`, `aggregateAttributionGroups` (**pure**: `(channel, alias)` groups, one vote per folder per person, demotions carried up, silent groups kept). A group carries `unanimous` — every *suggested* folder names every voted person — because `votes.length > 1` alone cannot separate a disagreement from a multi-person set (`FJ Michelle & Rebecca` is one decision, not a dispute), and 22.2% of catalogue sets name more than one participant + its query wrapper `getAttributionGroups`. Suggestions carry `tier` (`EXACT|STRONG|WEAK`) and `demotions[]` (`CROSS_LABEL|UNKNOWN_CHANNEL|AMBIGUOUS|DATE_VARIANT`) — *why* it is doubtful, not just how much. Nothing here materialises a Set, participant or Contact. Written by `catalogue-match-service` in the app (S5; the catalogue-join agent and its POST are retired, the route remains for other sources).

**`lib/channel-label.ts`** — `channelDisplay(item)` → `{ label, importedAs }` (pure, unit-tested). `StagingSet.channelName` is **provenance**, not the display source, and it disagrees with `Channel.name` in two different ways: **26,340 rows are the same name respelled** ("KATYA CLOVER" vs "KatyaClover") — noise, folded into the record's name; **1,955 rows across 42 channels are a different name mapped on purpose** ("ALS ARCHIVE" → ALSScan, "ONLYTEASE COVERS" → OnlyTease: a base channel and its archive/cover feed) — kept beside the label, because it carries what the record does not *and* because a wrong mapping ("ALSANGELS" → ALSScan) is visible only through it. The test for "merely respelled" is case, accents and separators, deliberately nothing cleverer. `channelLabel` returns just the label. Not used in the import-vs-set comparison grid, where the raw value is the subject of the comparison.

**`lib/media-url.ts`** — `buildUrl` plus **`localMediaUrlOrNull`**, the guard for a standing rule: **the app never renders or fetches media from an external URL.** Harvested URL fields (`Contact.thumbUrl`, some `StagingSet.coverImageUrl`) point at the source site, which is hotlink-protected — 200 to a request with no `Referer`, **403 to a browser**, which always sends one — so they render as broken-image icons and leak a referrer. They are provenance, never a rendering source. `next.config.ts` restricts `images.remotePatterns` to the MinIO host, but that binds `next/image` only; a raw `<img src>` walks past it, so the guard belongs where a URL leaves the service layer. Want a remote image? Import it into MinIO with an agent.

**`person-reference-service.ts`** — `resolvePersonReferences`, a face to compare an archive cover against. Deciding "is this her" from a name is guesswork, and every comparable tool puts a reference image beside the candidate. The difficulty is coverage: of 5,074 suggested identities only 94 are curated Persons and 711 are Contacts, so the resolution runs down a ladder — **Person headshot → catalogue portrait → covers of folders already confirmed as that person**. `Contact.thumbUrl` is deliberately not a rung — it is hotlink-protected and cannot render. The last rung needs no import and no agent, sits at 100% cover coverage, and improves as the operator works.

**`catalogue-inventory.ts`** — pure logic of the read-only catalogue inventory (ADR-0038), shared by `scripts/catalogue-inventory.ts` and its tests: `inspectFolder` judges one catalogue folder with the import parser and sorts its problems into quarantine Q1–Q5 / flag F1–F6; `buildInventory` adds cross-folder checks (Q5 duplicate ICG-IDs, app-refused portraits) and the go/no-go numbers (health, overlap I1–I4, payoff for staged casts / archive / network, projected cost). **`catalogue-inventory-context-service.ts`** — the app's side: Person and Contact ICG-IDs, catalogue portraits (stored / refused), open staged sets with a cast member who is not a developed Person (a thin Contact is not recognisable), database size, and the channels (app channels with their import aliases, sets and open staged sets without a channel, archive channel folders per name).

**`catalogue-avatar-service.ts`** — person portraits harvested from the catalogue, keyed on the **ICG-ID alone** because 4,269 of 5,074 suggested identities have neither a Person nor a Contact to hang one off. Mirrors `archive-cover-service.ts` (`key`/`error`/`checkedAt`): one bad image fails one person, the reason is stored rather than logged, a re-run retries only failures, and Sharp stays strict. Agent: `scripts/catalogue-avatar.ps1`; endpoints `GET /api/catalogue/avatars` (which ICG-IDs are already held, so a re-run uploads only what is new) and `POST /api/catalogue/avatar/[icgId]`.

**`lib/archive-match-label.ts`** — `describeMatchLabel`, pure and shared by the staging browser, the archive banner and the media queue so they cannot drift into three vocabularies. **A badge must never claim agreement it does not have.** The old label was inferred from the confidence alone (`HIGH ? 'date+code' : 'title match'`), but HIGH can be earned by an exact title on its own — so a folder dated 2018-02-10 was announced as a "date+code" match for a set released 2018-02-13. `SuggestedFolderInfo` now carries the measured truth (`dateMatches`, `titleMatches`, `dayDelta`) and the label states the drift in days, so a wrong folder date is visible instead of confirmed on trust.

**`archive-stub-service.ts`** (ADR-0032) — Stub archive folders: a deliberate placeholder copy, upgraded in place later. The flag is on `ArchiveFolder` (`stubSince`/`stubReason`/`stubNote`), not the Set — the publication is complete, the copy is not; `Set.isComplete` and `ArchiveStatus.INCOMPLETE` keep their meanings. `markArchiveFolderStub` (keeps the first date on an edit), `endArchiveFolderStub` (clears it, sets `stubEndedAt`, resets the folder cover via `clearArchiveFolderCover` — the same consequences whichever side ends it), `dismissStubEnded`. Pure half in `lib/archive-stub.ts`: `toArchiveStub`, labels, `isStubMarkerName` (`.pb\STUB`, any extension) and `reconcileStub`, the three-way reconciliation between the flag and the marker file using the remembered `stubDiskState` (disk moved → adopt; app moved → agent writes/removes; both moved → they agree; never reported → union). A content change never ends a stub. **Disk side:** `archive-scan.ps1` reports `stubOnDisk` (+ `stubNote`, the file's text) for every leaf of a Full run and never skips a folder carrying `STUB` (overwritten media leave the mtime alone); `upsertArchiveFolders` ends with `reconcileStubsFromScan` (only items whose `stubOnDisk` is a boolean — "not looked" must never read as "deleted"; a disk-set stub gets `stubReason = null`; an end from disk runs `endArchiveFolderStub`), and the agent's write phase pulls `GET /api/archive/stub-writes` (`getStubWrites`: app flag ≠ last disk state) and creates/removes `STUB` — its only write for this feature. Surfaced by `ArchiveStubControl` (mark / edit / end popover) and `StubBadge` on the archive rows, the set archive panel + hero, and the staged-set row + panel; `ArchiveFolderEntry.stub`, `getSetById` and `ARCHIVE_LINK_SELECT` (import/staging-set-service) carry the fields. Actions: `archive-stub-actions.ts`.

**`archive-tag-service.ts`** (ADR-0034) — Tags on archive folders, given at filing time. Before promotion they are `ArchiveFolderTag` rows (`TaggableEntity` `ARCHIVE_FOLDER`, domains CONTENT/ANY, own tags only — no inheritance); once a CONFIRMED link joins the folder to a Set they are the Set's `SetTag`s (`folderTagOwner`). Ownership heals itself rather than being wired into every link path: `absorbFolderTagsIntoSets` moves leftover folder rows to the Set (called from the scan reconcile, the list rows and `markStagingSetPromoted`), and `ArchiveFolder.tagsSyncedOwner` makes an owner change unite instead of deleting markers. Pure half in `lib/archive-tags.ts`: `parseTagMarker` (`#name`, `#group=name`, extension/`_`/case tolerant), `resolveTagMarkers` (name/slug/alias, unknown + ambiguous + wrong-domain → unknown, an exclusive group with two markers → conflict, left out), `canonicalTagMarker`, `reconcileTagSet` (`reconcileStub` per tag id against `tagsDiskState`; `holdDiskRemovals` while the folder has unknown markers — a renamed tag must never read as a deleted file). The `#group=` part only disambiguates (falls back to an unambiguous name after a group rename); `updateTagDefinition` keeps a renamed tag's old name as alias. **Disk side:** the scan reports `tagMarkers` on Full runs; `upsertArchiveFolders` ends with `reconcileFolderTagsFromScan` (after the stub reconcile); the agent's `Write-TagMarkers` phase pulls `GET /api/archive/tag-writes` (`getTagWrites`) and makes the `#…` files match `want` exactly. `resolveDiskTagName` teaches an unknown name (alias unless it is the tag's own name) and adopts it on every folder carrying it. UI: `ArchiveFolderTags` (archive rows, inline; `ArchiveFolderEntry.tags` from `getFolderTagViews`, batched via `getDirectTagsBatch`) and `ArchiveFolderTagsLoader` (staging slide panel → Annotations). Actions: `archive-tag-actions.ts` (`resolveDiskTagNameAction`, `getFolderTagsViewAction`). **Stage 2:** `tag-filter-service` treats a folder's tags as own ∪ confirmed Set's (`levelHas`, candidates, facets; `tag-predicates` `ownTagIds`); `WorkspaceFilters.tags` → `archiveTagScope` narrows the folder tabs and `getArchiveChannelSummaries`; `StagingSetFilters.tags` → `stagingSetIdsForTagQuery` (confirmed folder, or the promoted Set's folder). `entity-tag-service` bulk add/remove and `getSelectionTagCounts` route set-linked folders to their Set (`splitFolderOwners`). UI: `TagFilterInline` (button + query box + chips for client-filtered browsers, problems via `getTagFilterProblemsAction`; facets for `/staging-sets` via `getTagFacetsAction`), `/archive` **Select** mode with `BulkTagControls` (rows patched optimistically), the `/staging-sets` bulk bar, workbench `T` (`ArchiveFolderTagsLoader` in the inspector; the shell ignores keys from portalled dialogs), and folders in `getWorkflowTodo` / `countOpenTodos`. The tree view now reloads open channels after every summaries load (`loadOpenChannels`).
**`archive-unsettled.ts`** — `UNSETTLED_FOLDER`, the single definition of "still needs a person": no **CONFIRMED** link. The pipeline previously excluded any folder carrying an `ArchiveLink` at all, `SUGGESTED` included — treating a machine guess as a decision. The two failure modes compounded: a wrong suggestion removed the folder from the only view that could contradict it. Measured before the change: **2,733 folders hidden this way, 14% of their suggestions agreed with the folder on neither date nor title, and 0 had ever reached the catalogue agent** (its worklist used the same filter).

**Union rule (ADR-0028)** — `linkFolderToStagingSet` writes a folder's claims into a StagingSet's
cast only when that cast is **empty** (pure enrichment, what the develop path is for) or already
names the person (no-op). Emptiness is decided once, before anything is written, or the first
claim would fill the cast and block the second; a cast named without ICG-IDs still counts as a
cast. Withheld claims come back as `withheld` and the develop queue names them in an amber flash.
`createStagingSetFromOrphan` sets `titleNorm` — without it `findProbableStagingDuplicate` returns
null and a later import can never recognise the row (`scripts/backfill-staging-title-norm.ts`
catches rows made before the fix). The attribution queue carries the open contradiction count.

**A set's file count is its media (2026-08-08)** — `archive-scan.ps1` counts and
fingerprints only images and videos; sidecars, people files and OS clutter are ignored.
`ArchiveLink.archiveStatus = CHANGED` is derived purely from that count moving
(`ingestScanResults`), so counting tool-written files made the app read its own writes
as damage: the first people-file run flagged 276 sets. `ingestScanResults(results, { baseline: true })`
(`POST /api/archive/ingest?baseline=1`, agent switch `-Baseline`) stores the reported
counts without that inference — for the one run after a counting rule changes.

**`AttributionGroup.handMarked`** — folders in a group carrying a `FOLDER_ATTRIBUTION`
suggestion, counted in the pure `aggregateAttributionGroups` (one per folder, however many
markers it holds). Drives the queue's fourth view `?view=marked`, sorted most-marked first, and
the green badge on the group row. Without it a hand-placed marker is unreachable among ~8,900
leverage-ordered groups.

**Metadata folder `.pb\` (ADR-0030)** — all tool-written files live inside the set
folder's `.pb\`: `pulseboard.json` (identity anchor), `cast.json` (generated mirror,
`revision` first so the agent's 34k-folder staleness check stays a line scan) and the operator's
cast markers. `lib/archive-people-file.ts` owns the names (`META_DIR`, `ANCHOR_FILE`,
`APP_CAST_FILE`), the JSON render/parse and `parseCastMarkerName`. The agent reports
`max(leaf, .pb\)` as the leaf mtime — without it a marker dropped into an existing
`.pb\` would never be seen, because NTFS bumps only the direct parent. `-MigrateCast`
converts the older line files once.

**People files on disk (ADR-0029)** — `lib/archive-people-file.ts` (pure: `renderPeopleFile`,
`parsePeopleFile`, `peopleRevision` — first 16 hex of SHA-256, `EMPTY` when nobody is known) and
`services/archive-people-service.ts` (`getPeopleRevisions`, `getPeopleFiles`). Two agent endpoints,
`GET /api/archive/people-revisions` and `POST /api/archive/people-files`, both behind
`ARCHIVE_API_KEY`. The app cannot reach the archive filesystem, so `archive-scan.ps1` pulls: one
revision list per Full scan, header comparison per folder, batched body fetch, write or delete,
then a derived `{root}\.pb\index.tsv`. Inbound, the walk reads the cast markers and ships
`folderPeople` / `folderPeopleErrors` on `FullIngestItem`; `upsertArchiveFolders` writes them as
`FOLDER_ATTRIBUTION` suggestions at tier `EXACT` — **additive only**. Both fields pass through
`coerceFolderPeople` / `coerceStrings`, the same PowerShell single-element-array collapse that
`coerceVideoFiles` already guards. `services/set-cast-service.ts` (`loadCasts`) resolves both cast
shapes and is shared with the contradiction session.

**Import ↔ archive collision (ADR-0028)** — `services/import/linked-set-merge.ts`. During ingest,
`findLinkedCollision(channelId, date, isVideo, titleNorm)` looks for a StagingSet that already
carries a **CONFIRMED** archive link on the same key `findProbableStagingDuplicate` and
`findExistingStagingSet` use. On a hit the import **runs into that row** instead of creating a
twin: `fieldsToFill` writes only what the stub lacks (empty string counts as absent; `UNKNOWN`
precision counts as absent), `mergeCast` takes the cast from the import, and anyone it does not
credit is written back as a folder claim — except a cast member with no ICG-ID, who stays in the
cast because an attribution cannot represent them. Split imports (photo+video) decide each side on
its own and re-pair siblings. Reported as `merged` in `StagingIngestSummary`. **Blind spot:** an
import whose channel the matcher cannot resolve has no `channelId`, so no collision is detected —
the same gap the existing duplicate detection has.

**Attribution ↔ link contradiction detector** (ADR-0028) — `getAttributionLinkAudit()` (`maintenance-service.ts`)
surfaces archive folders whose confirmed attribution names someone the linked StagingSet/Set does
not list. The two truths are written independently and neither side reads the other:
`confirmArchiveLink` ignores the attributions (the attributed person is silently dropped at
promote), while `linkFolderToStagingSet` unions them into the participants — so the outcome
depends on which side was touched last. Read-only, takes no side (an import list can be
incomplete; a folder attribution is the owner's assertion, ADR-0027), and returns `checked` /
`comparable` alongside the rows so a 0 can be told apart from "nothing was comparable". Surfaced
on `/maintenance`; `scripts/detect-attribution-conflicts.ts --prod` runs it per tenant.
`scripts/import-test-snapshot.ts <ICG-ID>` (read-only) puts the four records that meet here — the
Person, her staged sets, the folders proposing her, and the links — on one screen, and flags the
cases that have gone wrong before: a link below HIGH, a folder proposing more than one person, a
ghost `Contact` left standing beside a Person. Runbook: `docs/agents.md`.
NOTE: the attribution queue only offers folders **without** a confirmed link (`UNSETTLED_FOLDER`),
so today the two populations are disjoint by construction and the detector reads 0/0 — it goes
live the moment an attributed folder is developed, linked or has a matcher suggestion confirmed.

**`services/conflict-session-service.ts`** — `getConflictSession()` builds the session rows (folder +
cover + the contested claim + the target's structured cast + faces for everyone via
`resolvePersonReferences`), and `resolveConflict(folderId, icgId, answer)` applies one of the three
answers. `components/archive/workbench/use-view-prefs.ts` holds the `I`/`T` preferences in a
`useSyncExternalStore` module store, so both sessions share them without a setState-in-effect.

**`lib/workbench-session.ts`** — the rules a workbench session runs on, pure and unit-tested: `dominantCandidate` / `defaultMode` (a candidate must carry **≥60%** of the group's suggested folders before the binary question is the right one — at 51% nearly half the folders answer "no", which is a folder-led pass wearing the wrong interface), `sessionFolders`, `sessionProgress`, `nextIndexAfterDecision` (the answered folder leaves the pass, so the next one has taken the current index — advancing to index+1 would skip a folder on every decision), `preloadWindow`, `letterboxColumn` (how wide the empty column beside an `object-contain` cover
is — what decides whether the identity overlay can sit *beside* a portrait cover instead of on
top of it), `nextOverlayLevel` + `readViewPrefs`/`writeViewPrefs` (the `I`/`T` view preferences,
persisted in `localStorage`).

**`attribution-confirm-service.ts`** — Per-folder attribution (ADR-0027, plan slices 5–6). `confirmAttributionGroup` writes `ArchiveFolderAttribution` rows and mints ghost `Contact`s (ADR-0022) — **it creates no Set, StagingSet or Person**. That split is measured, not stylistic: only 1.7% of the 28,377 suggestions point at a Person the app already has and 84.8% of suggested identities are unknown entirely, so bulk confirmation is identity *registration*; materialisation stays the curated per-person import path, which now arrives pre-informed about which folders are whose. **The unit of decision is the folder, not the group** (slice 6). `AA | Anna` holds several genuinely different people under one folder alias, so a group-level confirm could attach the wrong person to dozens of sets — the same failure Apple Photos documents when its batch confirm pulls in look-alikes and merges two people into one album, and the reason FamilySearch offers no bulk accept at all. `confirmFolderIdentity` / `rejectFolderIdentity` / `skipFolderIdentity` / `undoFolderIdentity` each act on one folder; `confirmFoldersIdentity` takes a hand-built selection (nothing is ever pre-selected, so the safety property sits in the selection). State lives in `ArchiveFolderReview` (`identity` × `develop`), written in the same transaction as the attribution rows. `planAttributions` remains pure and tested. Also `decideAttributionGroup` (`NOT_A_PERSON` / `SKIPPED` — the largest group in the archive is `W4B | w4b magazine`, 204 folders of a magazine title), `undoAttributionGroup` (drops verdict + its attributions; keeps the deduplicated contacts), `getAttributionQueue` (leverage-ordered; a group leaves the open view when its folders are all ruled on, and group-level `NOT_A_PERSON` / `SKIPPED` survive the agent's next run), `getGroupFolders` (resolves `coverUrl` server-side; `buildUrl` reads the tenant bucket via AsyncLocalStorage). **Stage 2** — `getDevelopQueue` (confirmed folders with no staging set, grouped by *person* because that is what the question is about), `developFolder` — **links to an existing StagingSet rather than duplicating it** (`findExistingStagingSet` / `linkFolderToStagingSet`: exact date + exact normalised title + no archive link; the channel is *reported*, not required, because folder codes and staging channel names legitimately diverge — `W4B` ↔ `WATCH4BEAUTY` — while a real disagreement means the key coincided). Coming at the archive from the disk side, 106 folders on xpulse corresponded to an unlinked staging set that arrived through a person's import. Otherwise it reuses `createStagingSetFromOrphan` + `addStagingSetParticipant` so the ICG-ID reaches promotion. Also `waitOnFolder`. **Last check before a new set** (2026-10-16): `folder-match-service.ts` `findStagingCandidatesForFolder(folderId)` — one raw SQL pass over `staging_set` (pg_trgm `similarity` on `titleNorm`, day distance, channel from `parsedShortName`, cast by attribution ICG-IDs or the folder-name alias in `participantNamesNorm`, the SUGGESTED link's target) → up to 8 candidates with `reasons`, `dayDistance`, local-only `coverUrl` (`localMediaUrlOrNull`, else the cover of the folder it already has), cast names, `linkedFolderName` (CONFIRMED to another folder → cannot take this one), `promotedSetId`; a title alone needs similarity ≥ 0.8, weaker titles need a second signal. Dates read in the display zone (stored at local midnight). Shown by `FolderMatchCandidates` in `CreateKnownSetSheet` (archive row "Create"); `linkFolderToCandidate` (refuses a set already holding a folder; promoted → `confirmArchiveFolderLink` follows to the Set; else `linkFolderToStagingSet`, which now also nulls a SUGGESTED link's `confidence`); `createStagingSetFromFolder({ createNew: true })` skips the silent `findExistingStagingSet` reuse once the operator has seen the candidates. Actions: `findStagingCandidatesAction`, `linkFolderToCandidateAction`.

**`staging-set-participants.ts`** — `addStagingSetParticipant`, extracted from `addStagingSetParticipantAction` so the archive develop path writes participants through the same code. A staging set carries four derived fields (`participants`, `participantStatuses`, `participantIcgIds`, `participantNamesNorm`) that must stay in step; two implementations is how they drift.

**`lib/attribution-candidates.ts`** — `candidatesForFolder`, **pure and outside the service layer on purpose**: the review grid is a client component and the service imports Prisma, so sharing through the service would drag `node:async_hooks` into the browser bundle. Offers the folder's own suggestions first, then the group's votes by weight — a shortcut to a keystroke, never an answer.

### App Shell & Scrolling (invariant)

`AppShell` (`components/layout/app-shell.tsx`) uses **independent scroll regions**, not document scrolling. The outer row is `flex h-screen overflow-hidden`; the chrome — `Sidebar` (left, `h-screen`, internal `overflow-y-auto` nav) and `TopBar` (top, persistent, shows the route's section label via `getSectionLabel()` + the mobile drawer trigger) — never moves. **Only `<main id="app-scroll">` scrolls** (`overflow-y-auto overflow-x-hidden`, no top padding so the sticky filter toolbar can stick flush under the top bar).

Invariants:
- The window does **not** scroll (`window.scrollY` is always 0). Use `getAppScrollEl()` (`lib/scroll-container.ts`) for any scroll read/write. Browse scroll-restoration (`person-list`, `set-grid`, `session-grid`) and the career year-jump all target the container's `scrollTop`.
- Because `<main>` is the scroll container, it is the containing block for `position: sticky` descendants. `BrowserToolbar` is `sticky top-0` and publishes its measured height to the `--toolbar-h` CSS var (ResizeObserver); nested sticky headers (`GroupHeader` level 1, career year headers) offset beneath it via `top-[var(--toolbar-h,0px)]`.
- `BackToTop` is rendered once in the shell, watches `#app-scroll`, and fades in past 600px.
- Nav items live in one place (`layout/nav-items.tsx`) consumed by `Sidebar`, `MobileDrawer`, and `TopBar` — do not redeclare them.

| Pattern | Where Used | Mechanism |
|---------|-----------|-----------|
| URL searchParams | `/people`, `/sets`, `/sessions`, `/projects` filters, sort, groupBy | `useSearchParams()` + `router.push()` |

### Grouping Architecture

Browser pages (`/people`, `/sets`) support a `groupBy` URL param. When active:
- Server loads up to 500 items (instead of the default 50-per-page cursor)
- Client groups the flat array using `computeGroups` / `buildNestedGroups` from `src/lib/grouping.ts`
- `sortGroupKeys` orders sections (alpha, year/newest-first, age-bracket order)
- `GroupHeader` renders collapsible section headers (level 1 = primary, level 2 = nested sub-sections)
- `useCollapseState` manages expand/collapse per section, persisted to sessionStorage
- Infinite scroll is disabled when groupBy is active (all items loaded at once)

### Key Fields

- **Set**: `externalId` (optional, unique) — external source ID from import files; `archiveKey` (optional, unique) — stable UUID propagated from ArchiveFolder at link-confirm time; survives folder moves and drive migrations
- **StagingSet**: `archiveKey` (optional, unique) — same as Set; copied to promoted Set via `markStagingSetPromoted`
- **ArchiveFolder**: `archiveKey` (**required**, unique, `@default(uuid())`) — stable folder identity UUID generated at first scan time; independent of Set/StagingSet link status; enables sidecar-based lookup for cross-drive folder move detection; `suggestedConfidence` (`'HIGH'` | `'MEDIUM'` | null) — set by `runMatchingPass`
- **ImportBatch**: `subjectIcgId`, `rawContent`, `status` (PARSING→REVIEW→IMPORTING→COMPLETED), `previousBatchId` (self-relation for versioning)
- **ImportItem**: `type` (PERSON/PERSON_ALIAS/DIGITAL_IDENTITY/CHANNEL/LABEL/SET/CO_MODEL/CREDIT), `status` (NEW/MATCHED/PROBABLE/BLOCKED/IMPORTED/SKIPPED/FAILED), `data` (JSON), `editedData` (JSON), `dependsOn` (String[]), `matchedEntityId`, `matchConfidence`
- **Person**: `icgId` (unique, mandatory), `status` (active/inactive/wishlist/archived), `rating`, `pgrade`. ADR-0026: `icgId` is either **external** (mirrors the outside database) or **self-assigned** (minted here, marked by a reserved `@`). There is no origin column — it is derived from the ID, so replacing a minted ID with a real one via `updatePersonIcgId` reclassifies the person for free
- **SetCreditRaw**: `resolvedPersonId` / `resolvedAliasId` / `resolvedArtistId` / **`resolvedContactId`**. The last one (plan slice 2) holds a participant whose ICG-ID is known but who has no curated Person yet — without it, promotion dropped the key and the credit decayed to a bare name resolvable only by ambiguous name matching. `repointContactToPerson` moves these onto `resolvedPersonId` (status → RESOLVED) **before** deleting the contact; the FK is `onDelete: SetNull`, so skipping that repoint would silently strip the key rather than fail
- **PersonAlias**: `type` (common/birth/alias), `nameNorm` for search. One `common` alias = display name
- **Era**: `isBaseline` (one per person, **dateless** — see ADR-0001), `isDraft` (auto-created via `findOrCreateEraForDate`; cleared by `updateEra` on any edit), `date` + `datePrecision` + `dateModifier` for non-baseline
- **ScalarDelta**: one row per attribute change, filed into an Era; has `attributeDefinitionId` + `value` + own `date`/`datePrecision`/`dateModifier`. Folded into `PersonCurrentState` via `app_recompute_person_current_state` SQL function (mirrors TS `foldScalarDeltas`)
- **PersonCurrentState**: cache table holding folded physical state per person (1:1). Recomputed in-tx with every fold-input mutation via `recomputePersonCurrentState(tx, personId)`. Unique index on `personId`
- **Session**: `type` (REFERENCE/PRODUCTION), `status` (DRAFT/CONFIRMED), `personId` (unique FK for REFERENCE type)
- **MediaItem**: `variants` (JSON — profile/gallery sizes), `focalX`/`focalY` (0-1 normalized), `hash` (SHA256), `phash` (dHash)
- **PersonMediaLink**: `usage` enum, `slot` (for HEADSHOT), `categoryId` (for DETAIL), entity FKs (`bodyMarkId`, etc.)
- **PhysicalAttributeGroup/Definition**: Admin catalog for typed scalar attributes — every ScalarDelta points at one definition. `statusBearing` (Boolean, default FALSE) gates the AttributeStatus UI per definition
- **PersonCurrentState.presentBodyFeatureTypes** (Slice 15): String[] of distinct mark + modification types where `status <> 'removed'`. Drives the hero's binary type-presence chips. GIN-indexed for future filter queries. Populated by `app_recompute_person_current_state`. Replaces the per-mark `heroVisible/heroOrder` UI; the legacy `has*` booleans stay in the schema until Slice 17 (people-search-service still queries them)
- **ScalarDelta.cause** (ADR-0007): `DeltaCause` enum (`NATURAL` / `SURGICAL` / `OTHER`). Drives the derived `AttributeStatus` (NATURAL / ENHANCED / RESTORED) on status-bearing attrs; cached in `PersonCurrentState.attributeStatuses` (JSON)

## 9. Key Architectural Invariants

1. **Hard deletes only** — No soft-delete, no `deletedAt`. All deletes cascade via `cascade-helpers.ts` inside `$transaction` blocks.

2. **Reference sessions** — Auto-created one-per-person (type=REFERENCE, `personId` unique FK). Cannot be manually created/edited/deleted/merged. The authoritative source for a person's photos.

3. **Guard clauses inside transactions** — All check-then-act patterns (e.g., "is this a reference session?") run inside `$transaction` to avoid TOCTOU races.

4. **Server actions are the write boundary** — Components never call services directly for mutations. Actions validate with Zod, call services, revalidate paths.

5. **Photo variants** — Every uploaded image generates: `master_4000` (WebP q88, 4000px LS — processing master, replaces raw original), `gallery_512` (WebP q85, 512px LS), `view_1200` (WebP q83, 1200px LS), `full_2400` (WebP q85, 2400px LS), `profile_128/512/768` (WebP q82, 4:5 cover crop). Legacy variants `original`, `gallery_1024`, `gallery_1600`, `profile_256` remain in DB for existing images (backward-compat). Stored as JSON in `MediaItem.variants`. URLs built via `buildPhotoUrls()` / `buildUrl()` from `src/lib/media-url.ts`. Lightbox uses `full_2400 ?? gallery_1600 ?? gallery_1024 ?? original`.

6. **Focal points** — `focalX`/`focalY` (0-1 normalized) on MediaItem. `focalStyle()` utility returns `{ objectPosition }` CSS. Variant regeneration is fire-and-forget via `/api/media/[id]/regenerate-variants`.


8. **Entity media linking** — DETAIL usage on PersonMediaLink can be categorized (`categoryId`) and linked to specific entities (`bodyMarkId`, `bodyModificationId`). Categories driven by `entityModel` field on MediaCategory. The first photo by `sortOrder` is the entity's body-map cover; reorder via `setEntityMediaCover` (entity-FK-scoped). (The `cosmeticProcedureId` column remains in the schema during the Slice 5 → Slice 17 soak but is no longer written by any code path.)

8b. **Alignment templates & Aligned images** (ADR-0013/0014) — `MotifTemplate` (aspect, `bakeLongSide`, target keypoints) binds to a locus `MediaCategory` (`MediaCategory.alignmentTemplateId`, 0:1). A baked **Aligned image** carries `MediaItem.motifTemplateId` + `motifProvenance` ({sourceMediaItemId, points, matrix}) — its identity, **never** `isAnnotation` (annotations are a separate crop/highlight concept). Aligned images are a derived copy in the reference session that retains provenance (re-bakeable). **Visibility:** excluded from the raw reference gallery and cross-session source pickers (`getPersonMediaGallery` / `getPersonMediaAcrossSessions` / `getPersonSessionsWithMedia` filter `motifTemplateId: null`), shown in their category (Details tab, with an "aligned" badge) and the cross-person Atlas (`/atlas`). Aligned headshots display via an aspect-preserving variant (not the 4:5 `profile_*` crop). The legacy `MotifTemplate.slot` weld was retired in ADR-0016 — every template is category-bound (the former profile slots are now `cat_profile_slot{N}` categories of the **Profile** group).

8c. **Profile framings are ordinary categories** (ADR-0016, slice 6e-2 landed) — the former 5 profile slots are categories of a **Profile** `MediaCategoryGroup` (`grp_profile`; `cat_profile_slot{N}`, Headshot = `isAvatarSource`). A category holds many aligned images; the displayed image per `(person, category)` is the **representative** (`PersonMediaLink.isRepresentative`; explicit, else most recent). The **avatar ≡ the Headshot representative**. The reference-session **ProfileManager** (`components/people/profile-manager.tsx`) is the home for filling framings (per category: rep image, ★ rep picker when >1, Standardize/Link). The people browser's **ProfileViewSelector** picks which framing's representative the cards show (Headshot = default; number-key hotkeys). The retired `slot`/`isAvatar` columns, `HEADSHOT` links, the Slot Manager, the metadata-panel/lightbox slot-assign UIs, and the `p-img` slot-label settings are all gone.

8a. **Image editing sources the master** — the crop/annotation editor (`AnnotationEditor`) always loads `urls.original` (the best-quality master: `master_4000` for new uploads, raw `original` for legacy), never a display variant, so edits aren't silently downscaled.

9. **SetParticipant is derived** — Rebuilt from SessionContribution via `rebuildSetParticipantsFromContributions()`. Never edited directly. The rebuild ends with `syncPromotedStagingCasts()` (`set-cast-service.ts`): staging sets PROMOTED into the set take its on-camera cast (`participants`, `participantStatuses`, `participantIcgIds`, `participantNamesNorm`; the subject when it left the cast), so the staged sets person filter follows a recast. No-op when already in step or when the set has no on-camera cast.

10. **Server action serialization** — Cannot pass arrow functions from Server → Client components. Use `.bind()` for callbacks (e.g., `onDelete={deleteAction.bind(null, id)}`).

11. **Era fold canon (ADR-0001)** — The mapping `(eras + scalar deltas + events) → current state` lives in two places: `foldScalarDeltas` (TS, `person-service.ts`) and `app_recompute_person_current_state` (SQL function). They must produce identical winners; opposite literal sort directions but same semantics. When changing one, audit the other.

12. **In-tx cache recompute (ADR-0003)** — Every mutation that writes a fold input (ScalarDelta, BodyMarkEvent, etc.) MUST end its `$transaction` with `recomputePersonCurrentState(tx, personId)`. The `PersonCurrentState` cache is the only thing the read path queries — it cannot drift because the mutation path can't commit without writing it.

13. **Event-derived status projections (ADR-0002)** — `BodyMark.status` and `BodyModification.status` are projections of their event logs. Every event mutation calls the matching `recompute*Status(tx, id)` helper from `cascade-helpers.ts` in the same transaction. (Legacy `CosmeticProcedure.status` followed the same pattern but is no longer surfaced — see invariant about the Slice 5 deprecation.)

14. **Era-linked participation lives on SessionContribution, not SetParticipant (ADR-0004)** — A Session is one shoot = one Era. A Set may be a compilation spanning multiple Eras for the same person. The `eraId` is therefore authored on `SessionContribution` (source of truth); `SetParticipant` is derived. `addSessionContribution` / `updateSessionContribution` propagate `eraId` across every contribution row for the same `(sessionId, personId)` in one tx.

15. **Baseline Era is dateless** — Every Person has exactly one baseline Era (`isBaseline: true`, `date: null`). It is folded first by virtue of its flag, not its date. The only hard temporal floor for sanity checks is the Person's birthdate.

16. **Draft Eras are nudges, not gates** — `findOrCreateEraForDate` and `autoClusterDeltaIntoDraftEra` set `isDraft: true` when they spawn an Era to host a quick-edit. Drafts behave identically to curated Eras; the flag is cleared on any user edit (`updateEra`). The History panel surfaces drafts with an amber dashed dot + pill.

17. **Emergent Era authoring (ADR-0006, Slices 7+8+9)** — The record-physical-change sheet has **no Era picker**. The user picks one of three intents: `on-date` (auto-cluster into a draft Era around the date, ±AUTO_CLUSTER_WINDOW_MONTHS), `dateless` (file into the person's dedicated dateless draft Era — semantically distinct from baseline), or `baseline` ("this was always true"). Initial radio value is inferred from history: if the person has no prior physical data, default to `baseline`; otherwise default to `on-date`. **Sticky-only-for-curated (Slice 8):** when a physical change is edited, the new intent/date routes through `autoClusterDeltaIntoDraftEra`. Source rules:
    - **Curated source** (`!isDraft && !isBaseline`) → deltas stay in source; date fields update in place.
    - **Baseline source** → deltas move only if the user explicitly picks a non-baseline intent.
    - **Draft source** → free re-cluster on every date/intent change.
    After any move, the source draft Era is garbage-collected via `deleteDraftEraIfEmpty` if it has zero remaining members. **Per-delta editing (Slice 9):** the same sticky-rule logic applies at delta granularity via `editScalarDeltaAction(deltaId, ...)` — used by the inline editor in the Undated drawer so individual changes can be dated without disturbing siblings.

18. **Curation nudge + promotion (ADR-0006, Slice 9)** — Draft Eras with ≥`NUDGE_THRESHOLD_DELTAS` (3) populated `ScalarDelta`s surface a soft inline nudge on the Overview History panel. Dismissal is per-Era in `localStorage` with `NUDGE_SUPPRESSION_DAYS` (7-day) freshness; SSR-safe via `useNudgeDismissal(eraId)`. Aggregate count of eligible drafts appears as a badge on the **Overview tab label** via `useDraftErasReadyCount(eras)`. Clicking the nudge opens an inline promotion sheet: name input + checkbox list of member deltas (default all checked). Save calls `promoteEraAction(eraId, personId, { name, splitDeltaIds })` — the source Era becomes curated (`isDraft = false`, `label = name`); unchecked deltas move out to per-date draft Eras via `autoClusterDeltaIntoDraftEra` (one per delta date). Refuses to leave the source Era completely empty.

19. **Undated drawer (ADR-0006, Slice 9)** — The dateless draft Era (one per person, `date IS NULL && isDraft`) renders as an **"Undated changes"** card with soft-amber treatment. Each member delta gets an inline `Set date` affordance opening `ScalarDeltaInlineEditor` — a per-delta mini-form with value + 3-way intent radio + date + cause (if status-bearing). Saving via `editScalarDeltaAction` re-clusters the delta into a dated draft per Slice 8's routing.

20. **`@` is reserved in ICG-IDs (ADR-0026)** — An ICG-ID is either **external** (mirrors the outside database, `[A-Z0-9]` only) or **self-assigned** (minted here, marked by `@` at a fixed offset). The two namespaces are disjoint *by enforcement*: `createPersonSchema.superRefine` rejects the marker on an ID entered as external, and `createStagingSetsForBatch` validates harvested participant IDs against `ICG_ID_EXTERNAL_RE` before creating a `Contact`. That disjointness is the whole guarantee — no ID the external database can issue in future can collide with a minted one. Origin is **derived** from the string (`isSelfAssignedIcgId`), never stored, so an ID correction reclassifies a person for free. Minting is server-side, probed against **both** `Person.icgId` and `Contact.icgId`, and mints once — never re-derived from a later-learned name or birth year.

21. **A folder carries claims, a set has a cast (ADR-0028)** — `ArchiveFolderAttribution` is *your* assertion about an archive folder; `StagingSet.participants` (→ `SetParticipant`, a cache rebuilt from `SessionContribution`) is who the publisher credited. Linking places them side by side and **never merges them**. A person may be written into a cast only when that cast is **empty** (pure enrichment) or already names them; where it names a different cast, the contradiction stands and is decided per folder with the cover in view. No state records it: every answer mutates data, so `getAttributionLinkAudit()` — computed, not stored — *is* the queue, and it reports `checked`/`comparable` so a 0 can be told from "nothing was comparable". When an import collides with an already-linked staging set it runs into it rather than creating a twin; the cast then comes from the import, and whoever falls out survives as a claim on the folder.

22. **Taking a value back / never-changing traits (2026-10-20)** — `deleteScalarDeltaAction(deltaId, personId)` deletes one ScalarDelta (any Era), GCs an emptied draft via `deleteDraftEraIfEmpty`, recomputes `PersonCurrentState`. `updatePhysicalChangeAction` takes `removeAttributeIds` (fields emptied in the Edit sheet; deleted from the source Era only). `recordPhysicalChangeAction` / `updatePhysicalChangeAction` / `editScalarDeltaAction` refuse intent `on-date` without a date (no silent fallback to Undated). ALWAYS_STATIC rows edit the baseline in place (`StaticAttributeEditor` → `recordPhysicalChangeAction` intent `baseline`) and list non-baseline deltas that override it (ADR-0005).

### `lib/icg-id.ts` (ADR-0026)
The single definition of the ICG-ID shape — replaced three copies of the same regex literal.
- `ICG_ID_RE` (either namespace) / `ICG_ID_EXTERNAL_RE` (marker rejected) / `ICG_ID_LOCAL_RE` (`XX-NN@RRR`)

- `isSelfAssignedIcgId(icgId)` — origin is **derived from the ID**, never stored

- `mintLocalIcgIdCandidate(prefix)` → one unprobed candidate; callers must check uniqueness
